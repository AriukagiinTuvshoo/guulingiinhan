# P12.3 — Deep security and production gate audit

## 1. Executive summary

**P12.3 STATUS: PARTIAL. Release decision: NO-GO. Production: NOT READY.**

Two reproducible code defects and one dependency vulnerability were fixed in the local candidate: family-scoped ancestry validation could miss a cycle through another family; repeated parent/child creation returned 503 instead of 409; and the installed production `sharp` version had a newly published patched advisory. The canonical graph now has a PostgreSQL transaction advisory lock shared by its creation APIs. No additional genealogy graph or migration was introduced.

The final backend suite passed **242 tests**, Ruff passed, and mypy passed on 30 application files. A controlled local PostgreSQL test ran six overlapping Family/Shared Root HTTP writes: each retained one edge and rejected the inverse edge. Both frontend builds and all 25 route regressions passed. These are local candidate results, not deployed or production evidence.

Read-only staging metadata confirmed private R2 buckets, zero browser-role table grants, migration head alignment, and no existing canonical cycles. It also confirmed that the required owner-supplied root couple/four-child structure is absent from the current root. Authenticated two-account staging and protected-media delivery were unavailable. Operational recovery and the actual production stack are unproven. These release gates prevent GO.

## 12. Auth security

LOCAL/source checks: random session tokens are stored as SHA-256 hashes; hosted cookies use HttpOnly/Secure/SameSite=None with an explicit HTTPS origin allowlist and mutation Origin guard; development cookies use Lax. Sessions expire after seven days. Logout removes the matching session; reset/change-password flows invalidate sessions. Active User and known-minor login checks apply on protected requests. Password hashing uses scrypt with random salts and constant-time comparisons.

Email tokens are expiring, one-use hashes and sent in URL fragments. Phone OTP is purpose/phone/challenge-bound HMAC, five-minute expiry, five-attempt lockout, resend cooldown and prior challenge invalidation. Verify.MN session confirmation binds the provider result to the expected challenge/user/phone and expiry. OIDC checks signed one-use state, nonce, issuer/audience and explicit subject-based identity; it does not silently merge by matching email. Verified phone/email identities resolve the same canonical User when linked to it.

The current phone-password path intentionally permits initial unverified phone registration/login; it does not establish verified ownership for recovery/identity assertions. These source rules and provider-fake regressions passed. Real SMS/email/OIDC delivery, production cookie/origin/redirect behavior and session revocation in an authenticated staging browser remain UNVERIFIED; live SMS/email work was previously deferred by the owner.
