## E2E failures: diagnosis, real defect found, and current green run

Three different causes were separated by measurement, not assumption.

1. Spec transport error (test bug, fixed). `e2e/admin-people-workflows.spec.ts` first seeded data through `page.request.fetch`, which sends no `Origin`/`Referer`; `backend/app/csrf.py::request_origin_allowed` rejects a source-less state-changing request, so every mutation returned `403` (`POST /families/{id}/persons failed with 403`). `curl` reproduced it exactly: with `Origin: http://localhost:3100` the request passes, without it `403 Forbidden`. The spec now calls the API inside the page context, like `e2e/admin.spec.ts`.
2. **Application defect (real, fixed).** `PersonPicker` in `app/families/clan/page.tsx` rendered its own `<form>` **inside** the clan page's `<form>`. A direct probe of the running page showed the sequence precisely: after `fill`, the input kept its value and the search button was enabled (React state correct); clicking 'Хайх' submitted the OUTER form, navigated, and the next probe found the whole subtree gone (`selects: []`, input absent) with **no** `persons/search` request. Fix: the picker row is now a plain `<div>` with `type="button"` and an explicit `onKeyDown` Enter handler, so nested-form submission cannot escape. Re-verified: the clan spec passes through save, roster privacy assertion and detach.
3. Environment starvation (not a product defect). Under `next dev` with a concurrent build, load reached `19.47` with `788 MB` available and both listeners then stopped accepting connections, so unrelated specs saw blank pages and 30/60 s timeouts (`waiting for getByRole('link', { name: 'Админ эрх' })`) while a direct browser probe of the same build showed the expected content and zero console errors. The earlier `webServer` startup timeout had the same origin: cold `npm run dev` compiled `/login` in `677ms` and answered `/tree`, `/admin/people`, `/families/clan` in 48-72 ms, so route compilation is not the constraint; concurrency is.

Two scoped follow-ups came out of that evidence. `playwright.config.ts` gained an opt-in `E2E_SERVER=production` mode that reuses the already built bundle via `next start` (CI default behaviour is byte-for-byte unchanged); with it the 9-test suite runs in 33.8 s instead of timing out. And the clan route is statically prerendered, so the spec now waits for the hydrated options before interacting and asserts each selection stuck (`toHaveValue`), instead of writing into pre-hydration DOM that React discards.

A third finding was real flakiness in this session's own new spec: after clicking the trash pager, reading the rows immediately could capture the previous page while the request was still in flight (it failed once with the oldest record missing and the page-1 set duplicated). The spec now waits for the row set to actually change (`expect.poll(...).not.toBe(before)`) and for the page counter to match, then applies the same membership, 25-rows-per-non-final-page, uniqueness and return-navigation checks.

Two test-side expectations were corrected without weakening them: the trash page must be checked against the actual `deleted_at DESC` contract (newest on page 1, oldest only on the last page), and name membership is read from the row's `<strong>` cell because the row text also contains the timestamp and the restore button label. Full 27-record coverage, per-page size bounds, page count, cross-page uniqueness and return-navigation checks are all retained.

## Release blockers and limitations

- Critical for the 90% gate — only external infrastructure can close the rest, and none of it can be claimed from this sandbox:
  - a real hosted run of `.github/workflows/verify.yml` (all three jobs, including the new build step in `e2e`) — GitHub Actions has never executed it here;
  - a deployed target with TLS, so HTTPS, cookie `Secure`/`SameSite` behaviour and the `NEXT_PUBLIC_API_BASE_URL` wiring are observed rather than configured;
  - object-storage (S3-compatible) credentials for upload/read/delete plus a real backup-and-restore exercise against managed PostgreSQL, not the synthetic local drill;
  - live email/SMS/OIDC providers for registration verification and password reset, which are currently faked in tests;
  - browser coverage for registration and e-mail/phone verification, which no spec exercises yet (the confirm step needs a token that is only observable inside the test process, so a real end-to-end pass requires a provider stub reachable from the browser — deliberately not solved with a test-only endpoint). Ownership transition is not a missing test but a missing product decision: no endpoint exists, so it is out of scope here and cannot be claimed either way.
- The PostgreSQL gates are verified only against a locally provisioned disposable PG16.16 cluster; CI's own PostgreSQL service and `docker run` restore step, and a hosted Actions execution of all three jobs, are still unobserved.

- Object-storage operations still span DB commits; `get_photo_content` and `delete_memory_photos` remain lock-free (only a check-vs-revocation window is left after the bulk-delete fix closed the duplicate-audit path). Not claimed as a confirmed race.
- Browser pagination uses offset pagination, so concurrent inserts/deletes can shift records between requests; it does not offer snapshot semantics.
- The clan slice is link-only by design: it cannot re-parent people or merge households, and the unresolved product decision remains whether a clan may list a household's member names in `clan-households` (currently gated on household membership only). Destructive re-parenting from the reference is deliberately not ported.
- The uncommitted `c7a4e8d901b2` draft migration had been edited to add `manage_settings`; databases that applied the older text are now reconciled forward-only by `f4c19a7b3d20` (verified on PG16 above). No applied revision was rewritten and no production downgrade was run.
- Restore drill is synthetic and local. Production backup, object-storage recovery, external email/SMS/OIDC, TLS/cookie behavior, deployment and provider infrastructure remain unverified.
