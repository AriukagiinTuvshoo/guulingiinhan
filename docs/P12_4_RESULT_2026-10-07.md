### Important implementation limits

- Search pagination is per resource type, 12 results per section; it is not a globally ranked combined feed.
- Birth-year filtering intentionally reuses the existing conservative minor policy. Additional death-year/relationship filters were not invented where the current endpoints do not support them.
- Timeline is a bounded overview: up to 100 marriages/events/memory candidates and 50 stories/archives per source, with a visible cap notice. Full content remains in its existing resource pages.
- References are content links in existing text, not a second genealogy or document storage system. They do not grant access to their targets. Public community output strips these references.
- Archive type is a human-readable annotation in the existing description, not a new database field. Protected images remain the supported media; OCR, arbitrary document uploads and GEDCOM were not added.
- QR invitations were not introduced: the existing recipient-bound email link and code avoid exposing or recreating invitation tokens for a generic share flow.

## C. Security and data integrity

**PASS in the local automated matrix.**

New search uses the existing authenticated family-scoped resource APIs. New relationship and timeline endpoints authenticate, check active Family membership, scope both requested Persons to that Family, enforce private Person visibility, and apply explicit guardian permissions before exposing sensitive minor information. Relationship traversal cannot pass through unauthorized private/minor Persons or foreign-family intermediaries.

Timeline does not turn parent-child relationships or a profile-view grant into permission to read minor events, biography, memory or media. Content links validate each target against the same Family, current visibility and relevant minor policy. Reader-side resolution omits restricted/deleted targets and their titles. Public Story/Memory/Archive output strips private reference tokens. Protected media APIs/storage and existing Person tags remain authoritative.

Invitation preview uses the existing token hash, recipient identity, verification and expiry/revocation rules. The existing acceptance mutation remains authoritative; the new UI cannot grant owner or global administrator privileges. Preview is read-only. Existing content and invitation mutations keep their existing audit logging.

New discovery/reference/preview responses use `Cache-Control: private, no-store`. There is no cross-Family result cache or localStorage source of truth.

P12.3 global ancestry transaction locks, whole-canonical-graph cycle checks, duplicate relationship conflict handling, consent/guardian rules and secure media were preserved. No new schema/migration or competing Person/Family/relationship graph was introduced. No real family records were seeded, removed or rewritten.
